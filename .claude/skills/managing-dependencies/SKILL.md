# Managing Dependencies

**Owns:** whether a package may exist in this repository at all, and what happens to it
at install and update time. **Does not own:** landing an already-open Dependabot PR
(`merge-dependabot`); CI configuration around dependency installs (`changing-gates`);
the semver consequence of a bump for this package's own consumers (`release-impact`).

## Where a dependency goes

| Group | `pyproject.toml` location | What it means | Installed by |
|---|---|---|---|
| Runtime | `[project] dependencies` | Ships in the built wheel; every `uv run` and every consumer install pulls it in | Everything |
| Dev | `[dependency-groups] dev` | Test/lint/type tooling (`pytest`, `ruff`, `mypy`, stub packages) | `just install` (`uv sync --all-groups`), `ci.yml`'s lint/test/coverage jobs (`uv sync --group dev`) |
| Docs | `[dependency-groups] docs` | `mkdocs-material`, `mkdocstrings` | `just docs`, `just docs-check`, `docs.yml`'s deploy job |
| Ops | `[dependency-groups] ops` | `boto3` — the R2 sync tooling under `scripts/`, never imported by the application itself | `just data-pull`/`data-push`/`data-status` (`uv run --group ops python scripts/data_sync.py ...`), `swing-daily.yml`'s CI job (`uv sync --locked --group ops`) |

`ops` exists specifically so `boto3` is not installed on every plain `uv run` — its own
comment in `pyproject.toml` says so. Reject in review: a new dependency added to `dev`
because "it's needed for a script," when the script in question only ever runs through
one of the `ops`-scoped recipes above. Conversely, a dependency the application's own
`src/swing_copilot/` imports never belongs in `ops` or `dev` — it belongs in
`dependencies`, full stop: the built wheel declares only `[project] dependencies` as its
requirements, so a `dev`/`ops`-only package imported from `src/` installs fine here and
`ImportError`s for anyone who installs the wheel (which is exactly what `just smoke`
catches).

## Range vs. pin

A runtime dependency in `[project] dependencies` declares a SemVer **range**
(`pydantic>=2.9`, `duckdb>=1.1`, …), never an exact pin. `uv.lock` already owns
reproducibility for this checkout and for CI (`uv sync --group dev --locked` fails
outright on a lockfile drift); a hand-pinned exact version in `pyproject.toml` buys
nothing over that and actively narrows what a downstream resolver is allowed to pick.

## Adopting a new dependency

Before adding one, this repository's convention (AGENTS.md) is a review recorded in the
PR, not a checkbox a linter enforces — nothing here mechanically blocks a bad add, so the
judgment has to actually happen and be visible to a reviewer:

- Active maintenance — not an abandoned package.
- License compatibility: MIT/BSD/Apache-class. A copyleft license needs a deliberate,
  stated reason.
- Minimal transitive footprint — a small direct API behind a large dependency graph is
  still a real cost.

`dependency-review.yml` runs on every PR and catches a newly introduced dependency with a
known vulnerability or an incompatible license *in that PR's diff*, before merge — but it
is a backstop for the mechanical part of this review, not a substitute for the
maintenance/license/footprint judgment above.

## Landing the change

- Run `uv sync --all-groups` (what `just install` does) after any dependency change.
- `uv.lock` is committed **in the same commit** as the `pyproject.toml` change that
  produced it. It is generated, never hand-edited — `.claude/hooks/guard.py` blocks a
  direct `Edit`/`Write` to `uv.lock` outright (and blocks writing to it via a shell
  redirect, `sed -i`, `tee`, or similar), specifically so it is always regenerated by
  `uv lock`/`uv add`/`uv sync`, never typed by hand.

## The two-layer supply-chain cooldown

Two separate mechanisms delay adoption of a very recently published version, at two
different points and by two different windows — knowing both keeps you from treating one
as a substitute for the other:

- **`[tool.uv] exclude-newer`** (`pyproject.toml`) is a resolve-time cutoff: `uv lock`
  and `uv sync` refuse to resolve *any* dependency — direct or transitive, for any
  command, any time someone runs them — to a version published after this timestamp.
  It protects every fresh install and every relock against a package version that has not
  survived in the wild for at least the cooldown window.
- **`.github/dependabot.yml`'s `cooldown.default-days: 7`** delays only *when Dependabot
  opens an update PR* for a newly published version, separately configured for the `pip`
  and `github-actions` ecosystems. It does not touch a manual `uv add`/`uv lock` at all —
  that is what `exclude-newer` is for.

They exist together because they close different gaps: `exclude-newer` protects a
resolve regardless of who triggers it; the Dependabot cooldown protects the one path
Dependabot itself controls (its own PR-opening), on its own independent schedule.

### Bumping `exclude-newer`

AGENTS.md carries the three-step procedure (edit the date to roughly *today minus 14
days*, `uv lock`, commit both files together). The judgment it does not state: the
"at least monthly regardless" clause is the load-bearing half. A cutoff left at a stale
date does not fail anything — it silently resolves an ever-older dependency set, so the
symptom is a security advisory the lock can't even see, not a red build.

## What the two security workflows catch

- **`pip-audit.yml`** runs on a weekly schedule (plus manual dispatch), exports the
  *locked* dependency set (`uv export --no-emit-project --format requirements-txt`), and
  runs `pip-audit` against it — a sweep of what is actually resolved today, independent
  of any PR.
- **`dependency-review.yml`** runs on every PR and reviews only that PR's diff — a
  vulnerable or incompatible dependency introduced *by this change*, before it merges.

They are complementary, not redundant: `pip-audit.yml` catches an advisory published
*after* a dependency already landed; `dependency-review.yml` catches a problem at the
moment of introduction.
