    01. 要件定義書（swing-copilot）¶

    文書情報¶

    項目 内容
    システム名（仮称） swing-copilot
    文書種別 要件定義書
    版数 1.3
    作成日 2026-07-20
    最終更新日 2026-07-28
    関連文書 00_human_preparation.md（人間の下準備チェックリスト）、02_project_plan.md（プロジェクト計画書）

    背景と目的¶

    米国株のスイング〜ポジショントレード（保有数日〜数ヶ月）を対象に、銘柄スクリーニング・分析・レポート作成までを自動化し、投資家本人の意思決定を支援するシステムを構築する。発注（実際の売買執行）は人間がSBI証券・楽天証券等を通じて手動で行い、完全自動売買はスコープ外とする。

    Part1調査の結論として、本システムは意思決定支援ツールとしては条件付きGoと判断されている。ただし「安定した利益」を実証する根拠は存在しないため、バックテストやペーパートレードで良好な成績が出た場合でも、ペーパートレード→少額実運用という段階的な検証ゲートを必須とする。本システムは投資助言を行わず、最終的な売買判断は常に人間が行う。

    実装は最終的にClaude Codeの自律実行（/goal）によって行うことを前提とする。そのため、本文書の全機能要件・非機能要件には、自律実装エージェントが実装完了を判断できるよう、検証可能な受け入れ基準を付す。

    利用者は日本在住の個人投資家1名（Python可）であり、1人で長期にわたり保守できることを最優先の設計方針とする。

    スコープ¶

    対象¶

    • S&P500構成銘柄（約500銘柄）を対象としたユニバース管理、株価・財務・ニュース・経済指標データの取得と保存（各データの取得時点・利用可能時点を保持）
    • ファンダメンタル品質フィルタとテクニカルシグナルによる2段階のスクリーニング・エントリー候補抽出
    • 収集したニュース・開示テキストと決定論的なスクリーニング文脈のエクスポート、Claude Codeスキルによる定性分析（ニュース解釈・開示解釈・スクリーニング評価）と、その結果の機械検証・レポート反映
    • 日次結果のCLI表示、監査用Markdown保存、Discord Webhookサマリ通知
    • 戦略のバックテストとペーパートレードの記録・成績集計
    • 上記処理を1コマンドで順次実行するオーケストレーション

    対象外¶

    • 証券会社APIを用いた発注の自動化（CON-01）
    • 完全自動売買（最終判断・発注は常に人間が行う）
    • 断定的な売買指示を含む投資助言の提供（CON-03）
    • yfinanceを本番のデータ基盤として利用すること（試作限定、CON-02）

    利用者・利用シナリオ¶

    利用者¶

    日本在住の個人投資家1名。Pythonでのコード読解・簡単な修正が可能。証券会社の米国株口座を保有し、発注は自身の判断で手動実施する。開発・保守は基本的に本人が単独で行う。

    利用シナリオ（コマンド実行〜判断の流れ）¶

    1. 利用者または GitHub Actions は1日1回、コマンド（uv run copilot-daily）を実行し、ユニバース更新・データ取得・スクリーニング・シグナル抽出・テキスト収集・分析入力エクスポート・レポート生成までを順次実行させる（FR-12）。この時点のレポートは定性分析欄が「未実施」の状態である。
    2. GitHub Actions の .github/workflows/swing-daily.yml が swing-daily スキルを起動する。スキルは analysis_input.json を読んで定性分析（ニュース解釈・開示解釈・スクリーニング評価）を行い、analysis_result.jsonを書き出す。uv run copilot-ingest-analysisがその結果を機械検証し、同じレポートの定性欄だけを埋めて再描画する（FR-08）。定性分析スキルは CI でのみ実行し、ローカルの対話セッションを代替経路にしない。
    3. 実行完了後、CLIに候補・ファンダ分析・定性分析・銘柄ごとのverdict（見送り推奨／懸念なし）・リスク管理チェック結果が表示され、同内容のMarkdownが保存される（FR-09）。
    4. 利用者はCLIの結論ファーストな一覧と銘柄別詳細を確認する（FR-05〜FR-09）。
    5. 利用者はレポート内容を踏まえて自身で売買判断を行う。verdictはあくまで定性情報に基づく推奨であり、最終判断は常に人間が行う。
    6. 廃止（2026-08-19）: copilot-decisionによる人間の判断結果の記録（FR-11）は、公開トラックレコード化に伴い撤去した。proceed判定はcopilot-track updateが仮想ポジションとして機械的に追跡する。
    7. 本番移行後は、実際にSBI/楽天等で手動発注する（本システムのスコープ外）。
    8. 上記のコマンド実行から判断記録までは1回あたり数分〜10分程度を想定する。無人実行の結果はDiscord通知（FR-09）で届くため、通知を先に確認してからレポートを開いてもよい。

    機能要件¶

    機能要件一覧¶

    ID 要件名 概要
    FR-01 ユニバース管理 S&P500構成銘柄リストの取得・更新・手動上書き
    FR-02 株価データ取得・保存 日足OHLCV（調整済み）の取得・保存、DataProvider抽象化
    FR-03 ファンダメンタルデータ取得 EDGAR XBRLデータの取得・正規化・キャッシュ
    FR-04 スクリーニング ファンダ品質フィルタによる母集団絞り込み（第1段）
    FR-05 テクニカルシグナル トレンド＋押し目検出によるエントリー候補抽出（第2段）
    FR-06 リスク管理チェック 銘柄単位の指値・逆指値・ATR14・1R・警告・市場状態判定
    FR-07 テキスト収集 銘柄別ニュース、新着8-K/10-Q、経済指標カレンダーの収集
    FR-08 定性分析（スキル連携） 分析入力のエクスポート、Claude Codeスキルによる解釈、結果JSONの機械検証とレポート反映
    FR-09 レポート・通知 CLI日次ブリーフ＋監査用Markdown＋Discord Webhookサマリ通知
    FR-10 バックテスト 戦略の履歴検証（手数料・スリッページ込み）
    FR-11 ペーパートレード記録（廃止） シグナル→判断→仮想約定→損益の記録・成績集計
    FR-12 日次バッチ 上記処理を順次実行するオーケストレーション（1コマンドで起動）

    各要件の説明と受け入れ基準¶

    FR-01 ユニバース管理 - 説明: S&P500構成銘柄リストを取得し、CSVキャッシュとDuckDBのスナップショット履歴へ保存する。明示的なas_ofではsnapshot_date <= as_ofの最新履歴だけを使い、未来の構成銘柄を見ない。通常live実行では更新周期に従い再利用または更新し、取得元の一時障害時にも保存済み履歴を安全側に利用できる。利用者は銘柄リストを手動で上書きできる。 - 受け入れ基準: - 銘柄リスト取得処理を実行するコマンドが存在し、実行後に約500銘柄のティッカーリストが永続化されていることをpytestで検証できる。 - 手動上書き用のファイルまたはコマンドが存在し、上書き後の銘柄リストが後続処理（FR-02〜FR-06）に反映されることをテストで確認できる。 - --as-of実行は、直前・同日・直後の3つの履歴からsnapshot_date <= as_ofである最新だけを選び、履歴がなければ価格取得・スクリーニング前に明確なエラーで停止することを検証できる。 - live実行は最新履歴の経過日数がuniverse.refresh_interval_days未満なら外部取得を行わず、同値以上なら1回だけ更新してCSVとDuckDBへ同じ生の構成銘柄を保存することを検証できる。 - live更新が失敗しても既存履歴があれば、そのスナップショット日と失敗理由を警告として記録・表示し、runをdegradedで完走する。既存履歴もなければfail-fastすることを検証できる。 - manual_include/manual_excludeは選択済みの生スナップショットへ決定的に適用し、手動追加銘柄を履歴やCSVへ混入させないことを検証できる。

    FR-02 株価データ取得・保存 - 説明: 各銘柄の日足OHLCVを取得し、企業行動調整済みのOHLCを共通の価格基準としてParquetに保存し、DuckDBから参照する。データ取得元はDataProviderインターフェースで抽象化し、試作期のyfinanceから本番移行時のEODHDへ実装を差し替えられること。プロバイダ固有の列構造や調整方式を後続処理へ漏らさない。 - 受け入れ基準: - DataProvider抽象基底クラス（またはProtocol）が定義され、少なくともYFinanceProvider実装が存在し、単体テストで日足OHLCVが取得・保存できることを確認できる。 - 既存コードを変更せずに新しいDataProvider実装を追加できる設計になっていることを、モック実装を用いたテストで確認できる（差し替え可能性の検証）。 - 保存されたデータをDuckDBから再読込し、取得時と同一件数・カラム構成で取得できることをpytestで検証できる。 - 株式分割を含むfixtureで、保存後のOHLCが同一の調整基準に揃い、シグナル・チャート・バックテストが同じ価格列を使用することをpytestで検証できる。

    FR-03 ファンダメンタルデータ取得 - 説明: SEC EDGAR公式API（edgartools使用）から、売上・利益・キャッシュフロー・自己資本等のXBRLデータを取得し、正規化してキャッシュする。各レコードに会計期間末・提出日時・アクセッション番号を保持し、指定した評価日時点で公表済みの値だけを取得できること。EDGARのレート上限（10リクエスト/秒）とUser-Agentヘッダー必須要件を遵守する。 - 受け入れ基準: - EDGAR APIへのリクエストがUser-Agentヘッダーを付与して送信されることをテスト（モックHTTPサーバー等）で確認できる。 - リクエストレートが10リクエスト/秒を超えないようレート制御されていることを、連続リクエストのタイミングを検証するテストで確認できる。 - 取得したXBRLデータが正規化されたスキーマ（売上・利益・CF・自己資本等の共通フィールド）でキャッシュされ、同一銘柄への再取得時にキャッシュが利用されることをテストで確認できる。 - as_of直前・同時刻・直後のfixtureにより、filed_at <= as_ofだけがスクリーニングおよびバックテストへ入ることを検証できる。 - 一時障害は各試行で10リクエスト/秒制限を守りながら合計3回までretryし、既定backoff後に成功する場合と上限到達時の例外伝播をfake clock/sleepで検証できる。設定・入力検証エラーはretryしない。

    FR-04 スクリーニング - 説明: ファンダメンタル品質フィルタ（黒字であること、財務健全性の基準を満たすこと等）と流動性フィルタにより、S&P500ユニバースから母集団を絞り込む（2段構えの第1段）。同じas_of時点で利用可能なデータだけを使う。 - 受け入れ基準: - フィルタ条件を満たす銘柄のみが出力されることを、既知の入力データを用いたpytestで検証できる。 - フィルタロジックが後述のプラガブルなインターフェース（NFR-07）に準拠し、フィルタの追加・組み合わせがコード変更なしに設定で行えることをテストで確認できる。

    FR-05 テクニカルシグナル - 説明: FR-04で絞り込んだ母集団に対し、トレンド系指標と押し目検出ロジックでエントリー候補を抽出する（2段構えの第2段）。初期実装のSMA・RSI（Wilder方式）・ATRはpandasで実装する。フィルタ・シグナルはプラガブルなインターフェースで実装し、設定でAND条件を明示して組み合わせること。候補は決定的な順位規則で最大10銘柄へ集約する。 - 受け入れ基準: - 少なくとも1つのトレンド系シグナルと1つの押し目検出シグナルが実装され、既知のOHLCVデータに対する出力をpytestで検証できる。 - 新しいシグナルクラスを既存コード変更なしに追加し、既存シグナルと組み合わせて実行できることを統合テストで確認できる。 - 同一入力・同一as_of・同一設定では候補の内容と順位が一致し、複数シグナルが同一銘柄の1つの候補へ集約されることをpytestで検証できる。

    FR-06 リスク管理チェック - 説明: 公開分析は読者の口座残高・保有銘柄を知らない。抽出された候補ごとに、run日終値、計画指値（終値 + entry_limit_atr_multiple × ATR14）、終値アンカーの逆指値、ATR14、1R（(limit_price - stop_price) / limit_price）、警告、市場状態による判定を返す。口座依存の株数・集中度・相関・損失上限は本番経路で計算しない。 - 受け入れ基準: - 終値・指値・逆指値・ATR14・1Rが既知の入力から期待どおり算出されることをpytestで検証できる。 - 価格またはATRが欠ける、あるいはストップ幅が無効な場合は、値を推測せず明示的なnot_calculableを返すことを確認できる。 - 広いストップ、決算近接、取得不能を銘柄単位のwarnings/reasonsで表現し、CASH_PRIORITYは候補を保持して地合い理由で見送り、REDUCE_ONLYは候補を保持した警戒ラベルだけになることを確認できる。 - 本番の設定・分析入力・Markdown・ターミナル出力に口座評価額、株数、ポートフォリオヒート、サーキットブレーカーが含まれないことを確認できる。

    FR-07 テキスト収集 - 説明: 銘柄別ニュース（Finnhub、60コール/分・ティッカー別）、新着8-K/10-Q（EDGAR）、経済指標カレンダー（FRED）を収集する。ニュースは、ソースが記事に付与した関連ティッカーと分類ラベルを併せて保持し、分析入力の枠を関連度の高い記事から埋める。 - 受け入れ基準: - Finnhubへのリクエストが60コール/分の上限を超えないようレート制御されていることをテストで確認できる。 - 各データソースの取得結果が共通のテキストデータスキーマで保存され、後続の定性分析（FR-08）の分析入力へ渡せることを統合テストで確認できる。 - Finnhub応答のrelated（関連ティッカー）とcategory（分類ラベル）が正規化して保持され、欠落・空文字・想定外の型では「宣言なし」として空に落ちることをテストで確認できる。 - 分析入力のニュース枠は、関連ティッカーに対象銘柄を含む記事を、含まない記事より先に埋める。含まない記事（セクター横断記事・他社記事・定型マーケットサマリ）は降格であって除外ではない——関連記事がanalysis.max_news_items_per_symbolに満たない銘柄では、降格された記事が残りの枠を埋め、枠が空になることはない。関連ティッカーの宣言が無い記事は降格しない（宣言なしと無関連は別物であり、ティッカーを付さないソースをソースごと不利にしない）。 - 同一入力・同一as_ofではニュースの選別結果と順序が一致し、収集順に依存しないことをオフラインのfakeでpytest検証できる。

    FR-08 定性分析（スキル連携） - 説明: ニュース・開示テキストの解釈とスクリーニング結果の定性評価は、PythonからLLM APIを呼ばず、Claude Codeスキル（.claude/skills/swing-dailyとその配下の専門家スキル）が担う。Python側の責務は次の3点に限定する。(1) 日次バッチのステップ6で、候補ごとの決定論的文脈（スコア内訳、指値・逆指値・1R・warningsを含む銘柄単位のリスク制約、過去判断）と収集済みの未信頼テキストをanalysis_input.jsonとして日付付きレポートディレクトリへ原子的に書き出す。(2) スキルが書いたanalysis_result.jsonをcopilot-ingest-analysisが読み、strictスキーマ・provenance・CON-03で機械検証する。(3) 検証を通った定性セクションだけでレポートを再描画する。スキルの出力は一切信頼せず、決定論的な数値（スコア・順位・価格・1R・リスク判定）は分析側から書き換えられない。 - 受け入れ基準: - analysis_input.json・analysis_result.jsonが双方向ともpydanticのstrictスキーマ（extra="forbid"）で検証され、未知フィールド・スキーマ違反がエラーとして検出されることをpytestで確認できる。 - 出力スキーマが「事実（facts）」と「解釈（interpretation）」を別フィールドとして強制し、factsの各要素が非空・非空白のsource_idsを1件以上持つことを検証できる。 - 引用されたsource_idsが、当該銘柄についてanalysis_input.jsonで実際に供給したID集合の部分集合であることを検証できる。部分集合でない銘柄はfail-closedで縮退表示となり、リトライしないことをテストで確認できる。 - factsの各要素は、そのsource_idsが指す本文（ニュースなら見出し＋要約、開示ならanalysis_input.jsonが渡したtext、カレンダーイベントならタイトル＋要約）からの逐語引用evidence_quote（正規化後12〜300字）を持つことを検証できる。evidence_quoteが欠落している場合、または引用元として申告したsource_idsのいずれの本文にも（Unicode NFKC正規化・記号統一・空白畳み込み・大小無視のうえで）出現しない場合は、当該銘柄がfail-closedで縮退表示となり、リトライしないことをテストで確認できる。これにより、他銘柄の本文を読みながら自分の正しいsource_idsを申告するような取り違えを機械的に検出できる。 - 書類種別・提出日・ソースURLといったコード側メタデータはanalysis_input.jsonから解決され、スキル出力の申告値をそのまま採用しないことを確認できる。 - facts、interpretation、risk/red flag、YoY変化、スクリーニング評価、verdict理由を含む全ユーザー表示文字列についてCON-03検査をingest時に一元実施し、違反銘柄が表示されず縮退することを検証できる。 - analysis_input.jsonの候補symbolと候補内source_id、analysis_result.jsonのsymbolがそれぞれ一意であり、resultのsymbol集合がinput候補集合と完全一致しなければrun全体をhard failすることを検証できる。 - no_trade=trueでは非空白の理由を必須、falseでは理由をnullに固定し、Unicode NFKC正規化後にもCON-03の売買命令・義務表現を検出できることを検証できる。 - input由来URLはhttp/httpsだけをリンク化し、それ以外はattributionなしで安全に縮退することを検証できる。 - analysis_result.jsonのas_ofがanalysis_input.jsonのas_ofと一致しない場合はrun全体のhard failとし、部分的に読み込まないことを確認できる。 - 銘柄ごとのverdict（proceed／skip）と、run全体のno_trade表示がレポートへ反映され、検証未通過・分析未実施の銘柄では「懸念なし」と誤読される表示が出ないことを確認できる。 - copilot-ingest-analysisがネットワークアクセスもスクリーニング再計算も行わず、report_context.jsonに保存済みのブリーフの定性欄だけを差し替えることをテストで確認できる。 - 通常のlive当日実行では、同一銘柄・戦略の過去の人間判断を最大3件まで構造化してanalysis_input.jsonへ含められる。過去判断は現在の事実でも指示でもない旨を明記し、専用delimiter内でescapeする。 - --dry-run、バックテスト、明示的な--as-of実行では過去判断を分析入力へ渡さず、先読みを防ぐことをテストで確認できる。

    仕様変更（P7、スキル移行時）: 旧LLM統合にあったcatalyst_quality（触媒の質、表示専用）とguidance_direction（ガイダンス方向性）は新しい分析契約に含めず廃止した。いずれもランキング・リスク判定へ接続されていない表示専用フィールドであり、必要になればanalysis/schemas.pyの任意フィールドとして復活できる。

    FR-09 レポート・通知 - 説明: 日次結果をCLIへ見やすく表示し、同じDailyBriefから監査用Markdownを生成する。DuckDBを正本とし、Markdownは再生成可能な派生成果物とする。Discord Webhook通知はデフォルトで有効とし、無人実行の結果を届ける主経路とする。 - 受け入れ基準: - copilot-dailyが進捗ログをstderr、最終ブリーフをstdoutへ出し、市場概況・候補順位・シグナル・リスク・定性分析（未実施ならその旨）・警告を確認できる。copilot-ingest-analysisは同じDailyBriefから同じレンダラで再描画する。 - reports/<run_date>/<run_id>.mdとreports/latest.mdを同一ディレクトリの一時ファイルから原子的に置換し、同日再実行の履歴を上書きしない。 - CLIとMarkdownが共通のDailyBriefを入力とし、表示形式ごとにデータ取得・判断ロジックを重複させない。 - notification.enabled: true（デフォルト）かつWebhook URLが設定されている場合に、モックWebhookエンドポイントへサマリ内容を含むペイロードが送信されることをテストで確認できる。notification.enabled: falseの場合は送信が行われないこと、trueでWebhook URLが無い場合は縮退せず設定エラーとして即座に失敗することをテストで確認できる。 - CLI・Markdown・通知内に断定的な売買指示（CON-03）が含まれないことをテストとレビューで確認できる。

    FR-10 バックテスト - 説明: 日次バッチと同じFilter/Signalロジックを使う決定的なポートフォリオシミュレータで戦略の履歴検証を行う。シグナルは当日終値確定後に生成し、約定は翌営業日以降に限る。entry_limit_atr_multiple が正のときは、終値＋ATR14倍率のDay指値を日足OHLCから近似し、指値未到達を不約定として記録する（既定0.0は従来の翌営業日寄付モデル）。財務データは提出日時点、価格データは評価日時点で利用可能な情報だけを使い、手数料・スリッページを織り込み、SPYをベンチマークとして比較する。終了日以前のユニバース履歴があればそれを使い、履歴が不足する場合は現在の構成銘柄へフォールバックして、生存者バイアスの限界をレポートに明記する。 - 受け入れ基準: - バックテスト実行コマンドで、手数料・スリッページを反映した損益曲線とS&P500ベンチマーク比較が出力されることを確認できる。 - 同一の入力データ・戦略設定でバックテストを再実行した場合、同一の結果が再現されることをpytestで検証できる（再現性の確認）。 - 手計算可能な1取引fixtureで、買いと売りの双方へ不利なスリッページと手数料が適用され、強制清算後の最終資産が厳密に一致することを検証できる。stopと最大保有日が同日に成立する場合はstopを優先する。 - $0構成期間中のバックテストレポートに生存者バイアスの限界に関する注記が含まれることを確認できる。 - バックテストの終了日より後のユニバース履歴を選ばず、履歴がない場合も現在構成銘柄で処理を継続して生存者バイアス注記を残すことを検証できる。 - 将来の価格・提出前の財務情報を参照しないこと、ギャップを含むストップ約定規則、最大保有日数、同時保有上限、資金不足時の候補順位をfixtureで検証できる。 - 指値価格の算出がリスク評価とバックテストで共有され、始値が指値以下／日中安値が指値以下／指値未到達の3ケースと、k感応度用の設定上書きをpytestで検証できる。

    NFR-03 性能 - 説明: 日次バッチの合計実行時間を35分以内に収め、無人の定時実行がワークフローの制限時間に収まり、手元で手動実行した場合にも許容できる待ち時間に収まるようにする。 - 受け入れ基準: バッチ実行ログから、開始〜終了までの所要時間が35分以内であることを確認できる（実行環境を問わない）。

    NFR-05 監査性 - 説明: 全実行・ステップ・候補・リスク評価・定性分析の入出力・人間の判断を記録し、特定のrun_idのレポート入力を後から再構成可能な状態を保つ。 - 受け入れ基準: DuckDBのスキーマに、実行・ステップ・シグナル/候補・リスク評価・収集テキスト・人間の判断それぞれに対応するテーブルが存在する。runs.config_hashは検証済みSettings・選択したStrategySpec・strategy_keyのcanonical JSON全体から算出する完全SHA-256指紋とし、同じ行のmetadata_jsonにはprovider名、data tier、実効ユニバースのsnapshot日・identity、アプリ版・メタデータschema版を秘密情報なしで保存する。定性分析の監査証跡はreports/<run_date>/<run_id>/に残るanalysis_input.json（分析へ渡した入力そのもの）・analysis_result.json（スキルの回答そのもの）・report_context.json（再描画に使ったブリーフのスナップショット）の3ファイルが担う。3文書はrun_id、as_of、strategy_key、入力のcanonical JSONから計算した完全SHA-256 digestで束縛し、いずれかが不一致なら既存レポートを変更せずhard failする。任意のrun_idのバッチ実行結果を、記録された入力参照と出力から再構成できることをテストで確認できる。

    fail-closed 検証を通らなかった内容を、推測で補ったり再試行したりせず、非表示（縮退）にする方針
    verdict 定性分析による銘柄ごとの推奨（proceed＝懸念なし／skip＝見送り推奨）。決定論的なスコア・順位は変更しない
    フェイルソフト 一部処理が失敗しても、可能な範囲まで処理を完走させる設計方針
    ペーパートレード 実資金を用いず、仮想的な売買として記録・検証する取引
    生存者バイアス 上場廃止銘柄が除外されたデータでバックテストすることによる成績の過大評価
    冪等性 同一処理を複数回実行しても結果が変わらない性質（本システムでは同日再実行への対応）
