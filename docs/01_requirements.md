## 背景と目的

米国株のスイング〜ポジショントレード（保有数日〜数ヶ月）を対象に、銘柄スクリーニング・分析・レポート作成までを自動化し、投資家本人の**意思決定を支援する**システムを構築する。発注（実際の売買執行）は人間がSBI証券・楽天証券等を通じて手動で行い、完全自動売買はスコープ外とする。

Part1調査の結論として、本システムは意思決定支援ツールとしては条件付きGoと判断されている。ただし「安定した利益」を実証する根拠は存在しないため、バックテストやペーパートレードで良好な成績が出た場合でも、**ペーパートレード→少額実運用という段階的な検証ゲートを必須**とする。本システムは投資助言を行わず、最終的な売買判断は常に人間が行う。

実装は最終的にClaude Codeの自律実行（`/goal`）によって行うことを前提とする。そのため、本文書の全機能要件・非機能要件には、自律実装エージェントが実装完了を判断できるよう、検証可能な受け入れ基準を付す。

利用者は日本在住の個人投資家1名（Python可）であり、1人で長期にわたり保守できることを最優先の設計方針とする。

## スコープ

### 対象

- S&P500構成銘柄（約500銘柄）を対象としたユニバース管理、株価・財務・ニュース・経済指標データの取得と保存（各データの取得時点・利用可能時点を保持）
- ファンダメンタル品質フィルタとテクニカルシグナルによる2段階のスクリーニング・エントリー候補抽出
- LLM（Claude API）によるニュース要約・決算書解釈
- 日次結果のCLI表示、監査用Markdown保存、Discord Webhookサマリ通知（オプション機能）
- 戦略のバックテストとペーパートレードの記録・成績集計
- 上記処理を1コマンドで順次実行するオーケストレーション（ローカルでの手動実行）

### 対象外

- 証券会社APIを用いた発注の自動化（CON-01）
- 完全自動売買（最終判断・発注は常に人間が行う）
- 断定的な売買指示を含む投資助言の提供（CON-03）
- yfinanceを本番のデータ基盤として利用すること（試作限定、CON-02）

## 利用者・利用シナリオ

### 利用者

日本在住の個人投資家1名。Pythonでのコード読解・簡単な修正が可能。証券会社の米国株口座を保有し、発注は自身の判断で手動実施する。開発・保守は基本的に本人が単独で行う。

### 利用シナリオ（コマンド実行〜判断の流れ）

1. 利用者は1日1回、任意のタイミングでコマンド（例: `uv run copilot-daily`）を実行し、ユニバース更新・データ取得・スクリーニング・シグナル抽出・LLM分析・レポート生成までを順次実行させる（FR-12）。
2. 実行完了後、CLIに候補・ファンダ分析・ニュース要約・リスク管理チェック結果が表示され、同内容のMarkdownが保存される（FR-09）。
3. 利用者はCLIの結論ファーストな一覧と銘柄別詳細を確認する（FR-05〜FR-09）。
4. 利用者はレポート内容を踏まえて自身で売買判断を行う。
   - P3（ペーパートレード検証）期間中は、`copilot-decision`で判断結果（見送り／仮想エントリー等）を記録する（FR-11）。
   - 本番移行後は、実際にSBI/楽天等で手動発注する（本システムのスコープ外）。
5. 上記のコマンド実行から判断記録までは1回あたり数分〜10分程度を想定する。Discord通知（オプション機能、FR-09）を有効にしている場合は、通知を先に確認してからレポートを開いてもよい。

## 機能要件

### 機能要件一覧

| ID | 要件名 | 概要 |
|---|---|---|

| FR-02 | 株価データ取得・保存 | 日足OHLCV（調整済み）の取得・保存、DataProvider抽象化 |
| FR-03 | ファンダメンタルデータ取得 | EDGAR XBRLデータの取得・正規化・キャッシュ |
| FR-04 | スクリーニング | ファンダ品質フィルタによる母集団絞り込み（第1段） |

| FR-06 | リスク管理チェック | ポジションサイズ・ストップ距離・セクター集中/相関チェック |
| FR-07 | テキスト収集 | 銘柄別ニュース、新着8-K/10-Q、経済指標カレンダーの収集 |
| FR-08 | LLM分析 | ニュース要約と決算書解釈（構造化JSON出力） |
| FR-09 | レポート・通知 | CLI日次ブリーフ＋監査用Markdown＋Discord Webhookサマリ通知（オプション機能） |
| FR-10 | バックテスト | 戦略の履歴検証（手数料・スリッページ込み） |

### 各要件の説明と受け入れ基準

**FR-01 ユニバース管理**
- 説明: S&P500構成銘柄リストを取得・保存し、定期更新できること。取得元の一時的な不整合等に備え、利用者が銘柄リストを手動で上書きできる手段を持つこと。
- 受け入れ基準:
  - 銘柄リスト取得処理を実行するコマンドが存在し、実行後に約500銘柄のティッカーリストが永続化されていることをpytestで検証できる。
  - 手動上書き用のファイルまたはコマンドが存在し、上書き後の銘柄リストが後続処理（FR-02〜FR-06）に反映されることをテストで確認できる。

**FR-02 株価データ取得・保存**
- 説明: 各銘柄の日足OHLCVを取得し、企業行動調整済みのOHLCを共通の価格基準としてParquetに保存し、DuckDBから参照する。データ取得元は`DataProvider`インターフェースで抽象化し、試作期のyfinanceから本番移行時のEODHDへ実装を差し替えられること。プロバイダ固有の列構造や調整方式を後続処理へ漏らさない。
- 受け入れ基準:
  - `DataProvider`抽象基底クラス（またはProtocol）が定義され、少なくとも`YFinanceProvider`実装が存在し、単体テストで日足OHLCVが取得・保存できることを確認できる。
  - 既存コードを変更せずに新しい`DataProvider`実装を追加できる設計になっていることを、モック実装を用いたテストで確認できる（差し替え可能性の検証）。
  - 保存されたデータをDuckDBから再読込し、取得時と同一件数・カラム構成で取得できることをpytestで検証できる。
  - 株式分割を含むfixtureで、保存後のOHLCが同一の調整基準に揃い、シグナル・チャート・バックテストが同じ価格列を使用することをpytestで検証できる。

**FR-03 ファンダメンタルデータ取得**
- 説明: SEC EDGAR公式API（edgartools使用）から、売上・利益・キャッシュフロー・自己資本等のXBRLデータを取得し、正規化してキャッシュする。各レコードに会計期間末・提出日時・アクセッション番号を保持し、指定した評価日時点で公表済みの値だけを取得できること。EDGARのレート上限（10リクエスト/秒）とUser-Agentヘッダー必須要件を遵守する。
- 受け入れ基準:
  - EDGAR APIへのリクエストがUser-Agentヘッダーを付与して送信されることをテスト（モックHTTPサーバー等）で確認できる。
  - リクエストレートが10リクエスト/秒を超えないようレート制御されていることを、連続リクエストのタイミングを検証するテストで確認できる。
  - 取得したXBRLデータが正規化されたスキーマ（売上・利益・CF・自己資本等の共通フィールド）でキャッシュされ、同一銘柄への再取得時にキャッシュが利用されることをテストで確認できる。
  - `as_of`直前・同時刻・直後のfixtureにより、`filed_at <= as_of`だけがスクリーニングおよびバックテストへ入ることを検証できる。
  - 一時障害は各試行で10リクエスト/秒制限を守りながら合計3回までretryし、既定backoff後に成功する場合と上限到達時の例外伝播をfake clock/sleepで検証できる。設定・入力検証エラーはretryしない。

**FR-04 スクリーニング**
- 説明: ファンダメンタル品質フィルタ（黒字であること、財務健全性の基準を満たすこと等）と流動性フィルタにより、S&P500ユニバースから母集団を絞り込む（2段構えの第1段）。同じ`as_of`時点で利用可能なデータだけを使う。
- 受け入れ基準:
  - フィルタ条件を満たす銘柄のみが出力されることを、既知の入力データを用いたpytestで検証できる。
  - フィルタロジックが後述のプラガブルなインターフェース（NFR-07）に準拠し、フィルタの追加・組み合わせがコード変更なしに設定で行えることをテストで確認できる。

**FR-05 テクニカルシグナル**
- 説明: FR-04で絞り込んだ母集団に対し、トレンド系指標と押し目検出ロジックでエントリー候補を抽出する（2段構えの第2段）。初期実装のSMA・RSI（Wilder方式）・ATRはpandasで実装する。フィルタ・シグナルはプラガブルなインターフェースで実装し、設定でAND条件を明示して組み合わせること。候補は決定的な順位規則で最大10銘柄へ集約する。
- 受け入れ基準:
  - 少なくとも1つのトレンド系シグナルと1つの押し目検出シグナルが実装され、既知のOHLCVデータに対する出力をpytestで検証できる。
  - 新しいシグナルクラスを既存コード変更なしに追加し、既存シグナルと組み合わせて実行できることを統合テストで確認できる。
  - 同一入力・同一`as_of`・同一設定では候補の内容と順位が一致し、複数シグナルが同一銘柄の1つの候補へ集約されることをpytestで検証できる。

**FR-06 リスク管理チェック**
- 説明: 抽出されたエントリー候補に対し、ポジションサイズ計算、ストップ距離の算出、セクター集中度・銘柄間相関のチェックを行う。
- 受け入れ基準:
  - ポジションサイズとストップ距離が既知の入力（資金量・ボラティリティ等）から期待される値で算出されることをpytestで検証できる。
  - セクター集中や高相関銘柄の組み合わせが検出された場合に警告フラグが出力されることをテストで確認できる。
  - 口座評価額、想定エントリー価格、ATRベースのストップ価格が欠けている場合は、株数を推測せず明示的な「計算不能」結果を返すことをテストで確認できる。
  - 相関は候補と保有銘柄の日次リターンを取引日でinner joinして計算する。日付ずれ・重複日・必要本数未満・定数系列では誤った相関値を返さずdata-quality警告になることを検証できる。

**FR-07 テキスト収集**
- 説明: 銘柄別ニュース（Finnhub、60コール/分・ティッカー別）、新着8-K/10-Q（EDGAR）、経済指標カレンダー（FRED）を収集する。
- 受け入れ基準:
  - Finnhubへのリクエストが60コール/分の上限を超えないようレート制御されていることをテストで確認できる。
  - 各データソースの取得結果が共通のテキストデータスキーマで保存され、後続のLLM分析（FR-08）へ渡せることを統合テストで確認できる。

**FR-08 LLM分析**
- 説明: 収集したニュースをLLMで要約し、決算書（10-Q/10-K）をLLMで解釈する。使用するモデルIDは`settings.yaml`の設定値（デフォルト: ニュース要約・決算書解釈ともHaiku）から取得し、コード変更なしに書き換えだけで使用モデルを切り替えられること（モデルIDのハードコード禁止）。出力は構造化JSONとし、出力スキーマによって事実と推測を分離する（例: `facts`フィールドと`inferences`/`speculations`フィールドを分離する）。
- 受け入れ基準:
  - LLM呼び出しの出力がJSON Schemaでバリデーションされ、スキーマ違反時にエラーとして検出されることをpytestで確認できる。
  - 出力スキーマが「事実」と「推測」を別フィールドとして強制する構造になっており、モックLLM応答を用いたテストで両フィールドの分離が検証できる。
  - ニュース要約・決算書解釈で使用するモデルIDが`settings.yaml`の設定値からLLMクライアントへ渡され、コードにモデルIDがハードコードされていないことをコード上で確認できる。デフォルトはニュース要約・決算書解釈とも`claude-haiku-4-5-20251001`とし、精度が必要な場合は`settings.yaml`の書き換えのみでSonnet等のモデルIDへ変更できる。
  - `settings.yaml`のモデルIDを変更するとAPIリクエストの`model`フィールドが追随することを、モックを用いたテストで確認できる。
  - 当月の記録済みコストと呼び出し前の概算コストが月額上限を超える場合、LLM呼び出しを行わず縮退レポートへ移行することをテストで確認できる。
  - 各factの`source_ids`が非空・空白不可で、入力ID集合の部分集合であることをfresh応答とcache応答の両方で検証できる。
  - system instructionとuser/untrusted本文がAPI上で分離され、外部本文がdelimiterを閉じようとしても命令として解釈されない形にescapeされることを検証できる。cache keyはsystem+userの完全なpromptを含む。
  - facts、interpretation、risk/red flag、YoY変化を含む全ユーザー表示文字列についてCON-03検査をgatewayで行い、違反応答がcache/表示されず縮退することを検証できる。
  - 通常のlive当日実行では、同一銘柄・戦略の過去の人間判断を最大3件まで構造化して渡せる。過去判断は現在の事実・指示ではないとsystem promptで明示し、外部本文とは別delimiter内でescapeする。
  - `--dry-run`、バックテスト、明示的な`--as-of`実行では過去判断をLLMへ渡さず、先読みを防ぐことをテストで確認できる。

**FR-09 レポート・通知**
- 説明: 日次結果をCLIへ見やすく表示し、同じ`DailyBrief`から監査用Markdownを生成する。DuckDBを正本とし、Markdownは再生成可能な派生成果物とする。Discord Webhook通知はオプション機能とする。
- 受け入れ基準:
  - `copilot-daily`が進捗ログをstderr、最終ブリーフをstdoutへ出し、市場概況・候補順位・シグナル・リスク・LLM分析・警告を確認できる。
  - `reports/<run_date>/<run_id>.md`と`reports/latest.md`を同一ディレクトリの一時ファイルから原子的に置換し、同日再実行の履歴を上書きしない。
  - CLIとMarkdownが共通の`DailyBrief`を入力とし、表示形式ごとにデータ取得・判断ロジックを重複させない。
  - `notification.enabled: false`（デフォルト）の場合、Discord Webhookへの送信が行われないことをテストで確認できる。`notification.enabled: true`かつWebhook URLが設定されている場合のみ、モックWebhookエンドポイントに対してサマリ内容を含むペイロードが送信されることをテストで確認できる。
  - CLI・Markdown・通知内に断定的な売買指示（CON-03）が含まれないことをテストとレビューで確認できる。

**FR-10 バックテスト**
- 説明: 日次バッチと同じFilter/Signalロジックを使う決定的なポートフォリオシミュレータで戦略の履歴検証を行う。シグナルは当日終値確定後に生成し、約定は翌営業日以降に限る。財務データは提出日時点、価格データは評価日時点で利用可能な情報だけを使い、手数料・スリッページを織り込み、SPYをベンチマークとして比較する。$0構成期間中は現在のS&P500構成銘柄を使うことによる生存者バイアスの限界をレポートに明記する。
- 受け入れ基準:
  - バックテスト実行コマンドで、手数料・スリッページを反映した損益曲線とS&P500ベンチマーク比較が出力されることを確認できる。
  - 同一の入力データ・戦略設定でバックテストを再実行した場合、同一の結果が再現されることをpytestで検証できる（再現性の確認）。
  - 手計算可能な1取引fixtureで、買いと売りの双方へ不利なスリッページと手数料が適用され、強制清算後の最終資産が厳密に一致することを検証できる。stopと最大保有日が同日に成立する場合はstopを優先する。
  - $0構成期間中のバックテストレポートに生存者バイアスの限界に関する注記が含まれることを確認できる。
  - 将来の価格・提出前の財務情報を参照しないこと、ギャップを含むストップ約定規則、最大保有日数、同時保有上限、資金不足時の候補順位をfixtureで検証できる。

**FR-11 ペーパートレード記録**
- 説明: シグナル発生から人間の判断、仮想約定、損益までを記録し、対S&P500での成績を集計する。
- 受け入れ基準:
  - シグナル・判断・仮想約定・損益がDuckDBに記録され、記録後にレコードを再取得して整合性を確認できることをpytestで検証できる。
  - `copilot-decision`は`run_id`と候補銘柄を検証し、戦略が一意なら推定して判断を記録する。候補外の銘柄は拒否する。
  - 判断記録後、当該runの生成済みMarkdownの判断セクションをDuckDBから原子的に更新する。
  - 成績集計コマンドを実行すると、累積損益とS&P500騰落率との比較が出力されることを確認できる。

**FR-12 日次バッチ**
- 説明: FR-01〜FR-06を基盤とし、FR-07〜FR-09を含めた日次処理を、利用者が1日1回コマンドで手動実行することにより順次実行するオーケストレーション。FR-10（バックテスト）とFR-11（人間の判断記録）は同じストアとドメインロジックを使う別CLIとして扱う。各実行に一意な`run_id`を付与し、同じ評価対象日を再実行しても自然キーupsertにより重複データを生成しない。LLM障害時もスクリーニングまでは完走するフェイルソフト設計とする。
- 受け入れ基準:
  - バッチ実行コマンドを同日中に2回実行した場合、2回目の実行が重複データを生成しないことをpytestで検証できる（冪等性の確認）。
  - 2回の実行が別々の`run_id`とステップ履歴を持ち、失敗した実行の後に再実行して正常完了できることをpytestで検証できる。
  - LLM API呼び出しを意図的に失敗させるモックを用いたテストで、スクリーニング・シグナル抽出・レポート生成（LLM分析部分を除く）までが正常完了することを確認できる（フェイルソフトの確認）。
  - ローカル実行時の所要時間が35分以内に収まることを、実行ログのタイムスタンプで確認できる。

### 各要件の説明と受け入れ基準

**NFR-01 コスト**
- 説明: 試作期（P1〜P2）はLLM費のみで月$5以内、本番運用（P3〜）は月$25以内に収める。
- 受け入れ基準: `llm_calls`の記録から当月の実績コストを集計できる。呼び出し前の概算額を加えると上限を超える場合はLLM処理をスキップして縮退レポートを生成し、上限超過を記録する。非同期で即日レポートに適さないBatch API対応はP1〜P2の必須範囲に含めない。

**NFR-02 保守性**
- 説明: 常時稼働サーバーを持たず、依存ライブラリを最小限に保ち、個人1人が長期間保守できる構成とする。
- 受け入れ基準: システム構成に常時稼働のサーバープロセス（デーモン）が存在しないことをアーキテクチャ図・実行構成から確認できる。構造化データの永続化はDuckDB、株価時系列はParquetに限定し、同一目的のDBを重複導入しない。TA-Lib・backtesting.py・SQLite専用データアクセス層はP1〜P2の依存に含めない。

**NFR-03 性能**
- 説明: 日次バッチの合計実行時間を35分以内に収め、利用者が1日1回ローカルで手動実行した際に許容できる待ち時間に収める。
- 受け入れ基準: ローカル実行時のバッチ実行ログから、開始〜終了までの所要時間が35分以内であることを確認できる。

**NFR-04 信頼性**
- 説明: データ欠損を検知し、外部API障害時にはフェイルソフト（処理継続）とリトライを行う。
- 受け入れ基準: 主要データソース（yfinance/EODHD, EDGAR, Finnhub, FRED）のいずれかが意図的に失敗するモックを用いたテストで、欠損が検知されログ等に記録されることを確認できる。一時的な障害に対してリトライ処理が行われることをテストで確認できる。
- 通常のpytest suiteはautouseのsocket遮断により実ネットワーク接続を即時失敗させる。外部portにはfakeを注入し、live canaryは通常suiteと成功条件から分離する。

**NFR-05 監査性**
- 説明: 全実行・ステップ・候補・リスク評価・LLM入出力・人間の判断を記録し、特定の`run_id`のレポート入力を後から再構成可能な状態を保つ。
- 受け入れ基準: DuckDBのスキーマに、実行・ステップ・シグナル/候補・リスク評価・LLM入出力・人間の判断それぞれに対応するテーブルが存在する。任意の`run_id`のバッチ実行結果を、記録された入力参照と出力から再構成できることをテストで確認できる。

**NFR-06 セキュリティ**
- 説明: APIキー等の秘匿情報をコードに含めず、ローカルの`.env`（`.gitignore`対象、python-dotenvで読み込み）で管理する。GitHubリポジトリを利用する場合（コード管理用、利用自体は任意）はプライベートリポジトリとする。
- 受け入れ基準: コード・設定ファイルにAPIキーがハードコードされていないことを、シークレットスキャン（例: `git grep`によるパターン検索）で確認できる。`.env`が`.gitignore`に含まれ、バージョン管理対象外であることを確認できる。GitHubリポジトリを利用する場合、プライベート設定であることを確認できる。

**NFR-07 拡張性**
- 説明: Strategy、Filter、Signal、DataProvider、Notifierをそれぞれ独立したインターフェースとして分離し、実装の追加・差し替えを容易にする。
- 受け入れ基準: 上記5種のインターフェース（抽象基底クラスまたはProtocol）がそれぞれ定義されており、各インターフェースに対して少なくとも1つの具体実装が存在することをコード上で確認できる。新しい実装を追加する際に既存の呼び出し側コードの変更が不要であることを、モック実装を追加するテストで確認できる。

**NFR-08 テスト品質**
- 説明: 「実際にアプリを動かしたときにバグがないレベル」の品質を、数値カバレッジとE2Eスモークテストの両輪で担保する。pytest-covによるline+branchカバレッジを全体で95%以上とし、`--cov-fail-under=95`を検証コマンドに組み込む。カバレッジ除外（`# pragma: no cover`）の使用は`if __name__ == "__main__":`ブロックとProtocol/ABCの抽象メソッド本体に限定し、テストのskip/xfailによるカバレッジ回避は禁止する。
- 受け入れ基準:
  - `uv run pytest`実行時、line+branchカバレッジが全体95%以上であり、`--cov-fail-under=95`のしきい値チェックを通過することを確認できる。
  - `# pragma: no cover`が付与されている箇所が`if __name__ == "__main__":`ブロックおよびProtocol/ABCの抽象メソッド本体のみであることを、コードレビューまたは`git grep "pragma: no cover"`等の確認手段で検証できる。
  - テストの`@pytest.mark.skip`/`@pytest.mark.xfail`がカバレッジ回避目的で使用されていないことを確認できる。
  - 外部API呼び出しを記録済みフィクスチャ/モックに差し替えた状態で`copilot-daily`相当のコマンドを一気通貫実行し、CLIブリーフとMarkdown生成まで正常終了（終了コード0）することをE2Eスモークテストとして検証できる。
  - `just verify`がruff、format check、mypy strict、line+branch coverage 95%以上のpytest、`mkdocs build --strict`、wheel smokeを非破壊で実行し、すべて終了コード0になることを確認できる。

## 用語集

| 用語 | 説明 |
|---|---|
| スイング〜ポジショントレード | 数日〜数ヶ月程度の期間ポジションを保有する株式売買スタイル |
| ユニバース | スクリーニング・分析の対象となる銘柄群（本システムではS&P500構成銘柄） |
| DataProvider | 株価データ取得元を抽象化するインターフェース。yfinance/EODHD等の実装を差し替え可能にする |
| XBRL | SEC EDGARが提供する財務データの構造化フォーマット |
| ファンダ品質フィルタ | 黒字・財務健全性などファンダメンタル指標に基づく銘柄の第1段絞り込み |
| プラガブル | インターフェースを介して実装を追加・差し替え・組み合わせできる設計方針 |
| Batch API | Claude APIのバッチ処理機能。通常料金の50%割引で利用可能 |
| フェイルソフト | 一部処理が失敗しても、可能な範囲まで処理を完走させる設計方針 |
| ペーパートレード | 実資金を用いず、仮想的な売買として記録・検証する取引 |
| 生存者バイアス | 上場廃止銘柄が除外されたデータでバックテストすることによる成績の過大評価 |
| 冪等性 | 同一処理を複数回実行しても結果が変わらない性質（本システムでは同日再実行への対応） |
