## 体制

- **人間（発注者）**: 1名。日本在住の個人投資家、Python可。要件レビュー、`/goal`実行の指示、実装成果物のレビュー、日々の運用（朝のレポート確認・判断記録）、予算・契約判断を担当する。
- **Claude Code（自律実装）**: `/goal`による自律実装エージェント。01_requirements.mdの各要件（FR/NFR/CON）と受け入れ基準に基づき、実装・テスト作成・検証を行う。実装過程で判断に迷う場合は要件定義書の受け入れ基準を根拠とする。
- 開発環境: Python 3.12、uv（パッケージ管理）、pytest（テスト）、ruff（リント）。ソースはプライベートGitHubリポジトリで管理する。

## フェーズ計画

### P0: 人間の下準備

- 期間目安: 0.5日
- 成果物: 00_human_preparation.mdのチェックリスト完了（P0対象項目1〜7, 10）。APIキー・`.env`の整備完了（Discord Webhook URLは通知を使う場合のみ）。
- 完了ゲート: 00_human_preparation.mdのP0チェックリスト項目がすべて完了していること。

### P1: 基盤構築

- 期間目安: 1〜2週間
- 対象要件: FR-01, FR-02, FR-03, FR-04, FR-05, FR-06, FR-10, FR-12（$0構成: yfinance＋EDGAR＋Parquet＋単一DuckDBで実装）
- 進め方: `/goal`による自律実装＋人間レビュー。
- 成果物: ユニバース管理・株価/財務データ取得・2段スクリーニング・リスク管理チェック・バックテスト機能・日次バッチオーケストレーションの実装一式とテストコード。
- 完了ゲート: バックテストが再現可能に動くこと（同一入力・戦略設定での再実行結果が一致することがpytestで確認できる）。加えて、line+branchカバレッジが全体95%以上であること（`--cov-fail-under=95`が通ること）。

### P2: LLM・レポート統合

- 期間目安: 1週間
- 対象要件: FR-07, FR-08, FR-09, FR-11
- 成果物: ニュース・EDGAR新着開示・経済指標カレンダーの収集、LLM分析、CLI日次ブリーフ、監査用Markdown、Discord Webhook通知（オプション）、判断記録CLI。
- 実装完了ゲート: line+branchカバレッジ95%以上、fixture/fakeによるCLI・MarkdownまでのE2Eスモーク成功、および設定済みの実キーが利用可能なら20銘柄のlive canary成功。
- P3開始前の運用ゲート: 日次バッチをローカルで7営業日連続して手動実行し、フェイルソフトを含め正常完了すること。時間経過を必要とするため、`/goal`によるP1+P2実装の完了条件には含めない。

### P3: ペーパートレード検証

- 期間目安: 3ヶ月以上
- 進め方: 毎朝、CLI日次ブリーフを確認し、`copilot-decision`で仮想売買（見送り／仮想エントリー等）を記録する。
- 成果物: 3ヶ月以上にわたるペーパートレード記録（シグナル・判断・仮想約定・損益）と対S&P500の成績集計。
- 完了ゲート: 対S&P500での成績・運用プロセスを評価し、継続／改良／中止のいずれかを判断すること。

### P4: 本番移行判断

- 期間目安: 判断・移行作業（P3完了後、期間は成績評価結果に応じて変動）
- 内容: EODHD契約（$19.99/月）の要否判断とAPIキー登録、生存者バイアスを排したバックテストの再実行、少額実運用への移行可否判断。
- 成果物: EODHD契約判断結果（契約する場合はAPIキー登録・delisted API利用可否のサポート確認済み）、再バックテスト結果、少額実運用移行可否の意思決定記録。
- 完了ゲート: CON-04に基づき、3ヶ月以上のペーパートレードで対S&P500評価を経た上で、実資金移行の可否が明示的に判断されていること。

## コスト計画

| フェーズ | データ費用 | LLM費用 | 月額上限（NFR-01） | 備考 |
|---|---|---|---|---|
| P0 | $0 | $0 | - | アカウント登録・キー取得は原則無料 |
| P1 | $0（yfinance, EDGAR: 無料） | $0（LLM未統合） | 月$5以内 | $0構成での基盤実装期間 |
| P2 | $0（yfinance, EDGAR, Finnhub無料枠, FRED: 無料） | 実績を`llm_calls`で記録（デフォルトは全処理Haiku） | 月$5以内 | 呼び出し前の予算ゲートで上限超過を防ぎ、超過見込み時は縮退レポートへ移行 |
| P3 | $0（$0構成継続） | 実績ベース | 月$25以内 | 上限は設定と予算ゲートで強制する |
| P4 | EODHD契約時の最新価格を契約前に確認 | 実績ベース | 月$25以内 | データ費とLLM費の合計が上限内に収まる場合のみ移行する |

- モデルIDと単価は変動する外部事実である。モデルIDは`settings.yaml`、単価はコード内の版管理された価格表で管理し、実装時にAnthropic公式ドキュメントと照合する。
- P1〜P2では即日レポートを優先し、非同期Batch APIは必須実装にしない。コストは呼び出し前の概算と記録済み実績で制御する。

## リスク管理表

| リスク | 影響 | 確率 | 対策 |
|---|---|---|---|
| yfinance停止リスク（非公式APIのため予告なく利用不可になる可能性） | P1構築中のデータ取得が停止し、$0構成での基盤検証が滞る | 中 | DataProviderインターフェース（FR-02/NFR-07）による抽象化を徹底し、代替実装（EODHD等）への切り替えを容易にしておく |
| 無料API仕様変更（Finnhub, FRED, EDGAR等のレート制限・仕様変更） | データ取得処理がエラーとなり日次バッチが失敗する | 中 | フェイルソフト設計（FR-12）とリトライ・欠損検知（NFR-04）で影響を局所化する |
| 実行忘れ（ローカル手動実行のため、その日のバッチを実行し忘れる可能性がある） | P3のペーパートレード検証期間中に一部日付のデータ・判断記録が欠落する | 中 | 実行しなかった日はその日のレポート・記録が単純に存在しないだけで、以降のデータ整合性やスケジュール前提は壊れない設計とする（冪等性・日付キー方式のため翌日以降の実行に影響しない） |
| 過学習（バックテストで戦略パラメータを過度に最適化してしまうリスク） | バックテストの好成績が実運用・ペーパートレードで再現しない | 高 | CON-04に基づき、バックテスト好成績のみで実資金へ進まず、3ヶ月以上のペーパートレードでの検証を必須とする |
| LLM幻覚（ニュース要約・決算書解釈での事実誤認） | 誤った情報に基づく判断支援が行われるリスク | 中 | FR-08の出力スキーマで事実と推測を分離し、各factに出典参照を保持する。レポートから原文を確認できるようにし、CON-03により断定的な売買指示は出力しない |
| モデル価格・提供状況の変更 | モデル切替時にLLMコスト上限超過またはAPIエラーが発生する | 中 | モデルIDを設定注入し、価格表を版管理する。呼び出し前の予算ゲートとフェイルソフトで影響を局所化する |
| モチベーション枯渇（毎朝のレポート確認・判断記録という運用負担） | P3のペーパートレード検証が中断し、3ヶ月以上の継続的な対S&P500評価ができなくなる | 中 | 00_human_preparation.mdの項目9で事前に運用習慣について合意し、確認作業を5〜10分程度に抑える設計（サマリ通知＋詳細レポートの二段構え）とする |

## 変更管理

- 本プロジェクト計画書・要件定義書・人間の下準備チェックリストは、いずれもプロジェクトの進行に応じて更新され得る。ただし、01_requirements.mdの要件ID（FR-01〜FR-12, NFR-01〜NFR-08, CON-01〜CON-04）は設計書・実装から参照されるため、**変更・追加・削除する場合は必ず発注者の承認を得た上で改版し、変更履歴を明記する**。
- ドキュメント更新時は、版数（文書情報セクションの「版数」欄）をインクリメントし、更新日と変更概要を記録する。
- P1〜P4の各フェーズ完了ゲートを満たさずに次フェーズへ進むことは原則禁止とする。やむを得ず前倒しで進める場合は、発注者が明示的に承認し、その判断根拠を本文書に追記する。
- CON-04（3ヶ月以上のペーパートレードで対S&P500評価を経ずに実資金へ進まない）は本プロジェクトの中核的な制約であり、いかなる変更管理プロセスにおいても緩和・削除の対象としない。
